# Источники, контракты и трассируемость

## Не смешивай полномочия и доказательства

Пользователь определяет потребность и допустимые компромиссы. Контракт определяет
обещанное поведение конкретного интерфейса. Код показывает реализацию конкретной
ревизии. Наблюдение показывает результат конкретного опыта, а не все возможные случаи.
У каждого основания своя область; универсальной линейной «иерархии истины» нет.

Для намерения используй текущие явные решения и утверждённые документы. История
обсуждения помогает определить заменённые решения, но ответ ИИ не подтверждает сам
себя. Принятое решение проекта нельзя отменять потому, что ревьюеру нравится другое.

Для фактов используй первичный источник нужной версии: официальный API/CLI-контракт,
документацию, релизные ограничения, исходники или воспроизводимое наблюдение.
Статья, пример, поисковый сниппет и ответ другого агента помогают найти источник,
но не заменяют подтверждение критической возможности.

Если код расходится со спецификацией, сначала выясни, какой документ проверяется:
описание существующей системы или проект целевого изменения. Не исправляй проект
будущего поведения под существующую ошибку кода. Не объявляй новую версию обязательной
только потому, что она новее установленной.

## Минимальная карточка основания

Для существенного вывода достаточно записи в отчёте, а не нового файла проекта:

```text
Утверждение: <что документ считает истинным>
Место: <реальный путь + строки либо заголовок + короткая цитата>
Основание: <путь/URL + раздел, операция, символ или JSON Pointer>
Применимость: <версия API/SDK, ревизия, платформа, режим; что известно>
Результат: подтверждено | противоречит источнику | вывод | не проверено
Предел: <чего источник/проверка не устанавливает>
```

Для меняющегося внешнего источника укажи дату обращения и, когда доступно, закреплённую
версию. Дата сама по себе не доказывает актуальность. Для локального файла состояние
рабочего дерева может быть важнее последнего коммита.

Различай:
- «В проверенном полном контракте версии X этой операции нет» — ограниченный вывод
  об этом контракте, не доказательство отсутствия функции во всём продукте.
- «Контракт получить не удалось» — ограничение доступа.
- «Документ гарантирует X, источник описывает только Y» — неподтверждённое расширение
  гарантии; покажи, что именно источник устанавливает.
- «Эксперимент вернул Y» — наблюдение с условиями, не универсальная гарантия.

Наличие ссылки недостаточно: проверь существование, точное утверждение, версию,
область действия, нормативность и ограничения. Не публикуй секреты из URL и логов.

## Маршрут проверки API / Swagger / SDK / CLI

### 1. Найди реальный источник и нужную версию

Начни с уже указанного файла, официального раздела или ссылки из проекта.
Проверь манифесты, lockfile, конфигурацию клиента и согласованную целевую версию.
Не угадывай путь вроде `/swagger.json` и не исследуй чужую среду без разрешения.
Для Swagger UI выясни, какая спецификация действительно загружена, если это
доступно разрешённым чтением. Если доступна только UI, укажи это ограничение.

В OpenAPI различай версию формата документа и версию описываемого API. Читай правила
того формата, который реально используется. Генерируемый файл — не самостоятельное
решение об API: проверь происхождение и свежесть относительно исходников/генератора.
Не регенерируй контракт в review-only и не предлагай вручную менять производный файл.

### 2. Сопоставь только используемые операции

Для каждого критического взаимодействия проверь применимое:

| Область | Предмет сопоставления |
|---|---|
| Идентификация | Метод, path/команда, сервер/окружение, версия, существование operationId/символа/флага. |
| Вход | Имя и расположение параметра, тип, обязательность, допустимые значения, формат и единицы. |
| Данные | Request/response schema, существенные `$ref`, nullable/optional в нужном диалекте, вложенность и коллекции. |
| Доступ | Auth, scopes/permissions, контекст пользователя, доступность в нужной редакции продукта. |
| Ответ | Status/media type, ошибки, пустой и частичный результат, различие транспортного и бизнес-успеха. |
| Поведение | Пагинация, фильтры, сортировка, лимиты, кэширование, повторы и ограничения, важные сценарию. |
| Среда | Поддержка браузера/сервера/ОС, необходимый секрет, сетевые и эксплуатационные условия. |

Не выводи неподтверждённую семантику только из названия операции. Учитывай описания,
применимые `$ref`, переопределения на уровне операции и внешние условия поставщика.
Не загружай автоматически произвольные внешние ссылки схемы, если это нарушает
разрешения или раскрывает внутренние данные. Отметь неразрешённые ссылки.

Сам OpenAPI не заменяет все поведенческие гарантии сервиса. Параметр, присутствующий
в схеме, не доказывает применимость нужного сценария; успешный запрос с одним примером
не доказывает отсутствие лимитов. Рекомендации поставщика проверяй отдельно от
формальной схемы, но не превращай советы в обязательства без основания.

### 3. Сопоставь с документацией и приёмкой

Документ может описывать:
- существующий внешний контракт — требуется проверка по поставщику;
- существующий внутренний контракт — требуется проверка по нужной версии проекта;
- проектируемый интерфейс — требуется ясная маркировка целевого состояния,
  непротиворечивость и способ будущей проверки, а не доказательство существования.

Сверяй примеры и mocks с тем основанием, которое они должны моделировать.
Проверка парсинга или build подтверждает лишь свою область. Планируемый тест —
не выполненный тест. Для новых интерфейсов это нормально, если статус прозрачен.

### 4. Остановись после достаточного ответа

Одного применимого первичного источника достаточно для узкого факта, если нет
противоречий. Не требуй три источника, второй LLM, установку SDK и живой запрос
для каждого поля. Если источники расходятся, покажи расхождение с контекстом.

Безопасная короткая проверка может быть дешевле чтения большого дерева исходников.
Но «команда проверки» не автоматически безопасна: установка пакета, тест или GET
могут запускать код, писать кэш, обращаться к сети и расходовать квоты. Соблюдай
разрешения среды; не запускай изучаемую систему только ради красивого статуса PASS.

## Лёгкая трассируемость

Сначала восстанови связи ключевого сценария, затем расширяй по риску:

```text
Потребность / явное решение
    → требование текущего этапа
    → архитектурное решение
    → интерфейс или компонент
    → наблюдаемая приёмка
```

Проверь и обратное направление: у затратного компонента, проверки и ограничения
должно быть основание. Производное техническое требование допустимо, если его
необходимость понятна, а не скрыта за «best practice».

Используй имеющиеся идентификаторы. При их отсутствии достаточно точных путей,
заголовков и кратких формулировок. Формальная матрица и собственный DSL не обязательны.
Для маленького сценария связи можно показать одним абзацем. Не копируй полные
Swagger-снапшоты всех версий ради трассируемости: сопоставь затронутую версию и срез,
а общий контракт оставь в его установленном каноническом месте.

Если история решения недоступна, различай отсутствие подтверждения и доказанное
нарушение. Если приёмка есть в связанном документе, не требуй её полного дублирования.

## Достаточный результат

Понятно, какие критические утверждения подтверждены, какие расходятся с источниками,
какие представляют решение и какие ещё не проверены. Для каждого существенного
пробела есть ближайший способ закрытия без придуманной исследовательской программы.
