# Примеры калибровки

Все сценарии условные. Операции, схемы, решения и результаты здесь — вымышленные
учебные входы, а не утверждения о возможностях реальных продуктов. Фрагменты «стало»
показывают предложение редакции; режим ревью сам файлы не меняет.

## 1. Спайк заменяется решением о продукте

**Вход:** цель — просматривать актуальные данные онлайн. Истории и офлайн-режима
в принятых требованиях нет. План требует выбрать локальную БД, спроектировать
миграции и провести двухдневный спайк по синхронизации.

**Слабое ревью:** «Спайк слишком длинный, сократить до дня».

**Полезное ревью:**

> В плане появилась постоянная копия данных и её синхронизация, но в текущем сценарии
> основание для этого не найдено. Это DECISION, а не доказанная техническая необходимость.
> Вариант A — текущие данные по запросу и временный кэш: меньше компонентов, но после
> перезапуска данные надо получить заново. Вариант B — локальная история: сохраняем
> данные между запусками, но добавляем хранение и правила актуальности.
> Для указанного сценария рекомендую A. Нужны ли история или работа без сети в первом этапе?

При ответе «не нужны» предложи убрать связанную работу и описать выбранный поток.
Не исследуй три БД. При ответе «нужны» уточни сценарий; необходимость БД и конкретный
спайк всё ещё требуют основания, а не следуют автоматически из слова «офлайн».

## 2. Актуальная модель вместо перечня отвергнутых стеков

**Вход:** пользователь явно выбрал Angular SPA и TypeScript. Условия учебного
сценария подтверждают доступность нужного API прямо из браузера. Настройки локальные,
данные загружаются по запросу; история не нужна.

**Было:**

> Не использовать Python. Не использовать PySide. Не использовать SQLite.
> Не создавать backend. Не добавлять ORM. Не реализовывать старую desktop-архитектуру.

**Предложение:**

> Приложение — Angular SPA на TypeScript. Браузер обращается к указанным операциям
> официального API. Клиент отвечает за отображение, объединение и фильтрацию данных.
> Пользовательские настройки хранятся в localStorage; временные данные — в памяти.
> Поставка состоит из статических файлов. Серверная логика и офлайн-история находятся
> вне текущего этапа.

Последнее предложение — полезная граница, а не мусор. Смысл ограничений сохранён.
Если план всё ещё содержит миграции БД, это уже отдельное смысловое противоречие,
а не только EDITORIAL. Исторический ADR с прежним стеком сохраняется с ясным статусом.
Не применяй этот пример как универсальную архитектуру к другим проектам.

## 3. Контракт ошибочен — исследование не нужно

**Вход:** документ называет существующей операцию `GET /v2/items` и описывает ответ
как `{ "items": [...] }`. Доступная полная схема той же версии для этой операции
описывает ответ `200` как массив объектов на верхнем уровне. Версия и окружение совпадают.

**Полезная находка:**

> DEFECT, подтверждено. Форма ответа в разделе «Загрузка списка» не совпадает со схемой
> `GET /v2/items → responses → 200`. При следовании тексту клиент будет читать
> несуществующую обёртку. Предлагаю исправить описание и пример по схеме, затем сверить
> с ней fixture контрактного теста. Спайк не нужен: ответ уже есть в доступном источнике.

**Контрпример:** если это предлагаемый новый внутренний endpoint, такая структура
сама по себе не ошибка. Сначала установи статус интерфейса. Если схема недоступна,
вывод «выдуманный контракт» недопустим: это GAP проверки.

## 4. Оправданный спайк

**Вход:** обязательный сценарий — уложиться в принятый бюджет памяти на конкретном
устройстве при обработке реального объёма данных. Поставщик описывает два применимых
режима, но не их расход памяти; документация и доступный код не дают достаточной оценки.
Отказаться от сценария нельзя в пределах текущих полномочий. Обычная маленькая
проверка не моделирует нужный объём.

**Полезный ответ:**

> Предлагаю кандидат на ограниченный спайк: сравнить два режима на утверждённом объёме
> данных в целевой среде. Результат определит выбор режима. Нужны минимальный измеритель,
> одинаковые входы и проверка принятого лимита. Предлагаемый бюджет необходимо согласовать.
> Если оба режима укладываются — выбираем более простой по согласованным критериям;
> если только один — его; если ни один или измерение неубедительно — возвращаемся к
> выбору ограничений и альтернатив. Запуск без разрешения не производится.

Скилл не должен удалять такой спайк ради механического «KISS». Достаточно узкого
вопроса и полезного результата; строить benchmark-платформу не требуется.

## 5. Полезный запрет и принятый компромисс

**Вход A:** «Секрет поставщика не включается в клиентский bundle». Это реальная граница
в учебном контракте и инструкции по размещению секрета.

**Ожидаемое ревью:** запрет сохранить. Можно яснее указать ответственную сторону,
но нельзя заменить его расплывчатым «безопасно работать с секретами».

**Вход B:** пользователь явно принял онлайн-only для MVP. Документ сообщает, что при
отсутствии сети приложение показывает состояние недоступности данных.

**Ожидаемое ревью:** TRADEOFF без требования реализации офлайн-режима. Не добавлять
локальную БД или новый вопрос о том же выборе. Вернуться к нему при новом офлайн-сценарии.

## 6. Источники расходятся

**Вход:** спецификация версии, используемой проектом, описывает обязательное поле;
пример в новой документации поставщика его не содержит. Реализация ещё не изменялась.

**Полезное ревью:**

> Проверяется версия, закреплённая проектом. Новый пример сам по себе не меняет её
> контракт. Для текущего этапа описание сверяется с применимой схемой; миграцию на
> новую версию предлагается обсуждать отдельно только при необходимости. Если разные
> источники именно одной версии противоречат друг другу, фиксируется конфликт источников,
> а не произвольно выбирается удобная схема.

Не требуй обновить зависимость ради соответствия самому новому примеру.

## 7. Нормальный результат без находок

**Вход:** маленькая согласованная спецификация, явные границы, доступный проверенный
контракт и понятная приёмка. Нет классов, ADR и отдельной матрицы трассируемости,
но все нужные связи читаются непосредственно из текста.

**Полезный ответ:**

> По проверенному сценарию препятствий для реализации не найдено. Требования согласованы
> с указанным контрактом, приёмка проверяема. Дополнительные ADR и спайки для этого среза
> не требуются. Вывод относится к перечисленным документам и версии; реализация кода
> в это ревью не входила.

Не выдумывай замечания, чтобы отчёт казался более основательным.
